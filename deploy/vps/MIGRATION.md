# Перенос ВАРГИ: рабочая последовательность

Решение от 6 октября 2026: основной сайт, интерфейс `/board/`, API и фотографии работают на одном доступном VPS, под доменом `xn----7sbbfg4a6clj5k.xn--p1ai`. Cloudflare в этой схеме не используется. Отказ у посетительницы на двух устройствах одной Wi-Fi сети не устанавливает точную причину; доступность нового сервера из этой сети — обязательная проверка до переключения.

Этот документ и конфигурация подготовлены для переноса. Новый VPS, оплата, загрузка живых данных и изменение DNS ещё не выполнены. Требуется Docker Engine, Compose 2.30+, Python 3 на Ubuntu/Linux и приватное внешнее резервное хранилище. Запуск и переменные описаны в [README](README.md).

## Данные и резервирование

Переносить полный приватный набор: `submissions/` со всеми статусами, JSON и фотографиями, `admin-auth.json`, `telegram-notify.json` при их наличии. Публичный `/listings` не является экспортом: он не содержит очередь модерации, корзину, auth и все внутренние поля. Исходные JSON и фото сохраняются побайтно, включая `requestId`/`requestHash`, чтобы повтор отправки после переноса не создавал новую заявку. Для старых записей без этих полей утилита выдаёт только счётчик.

Архивы, env и данные нельзя помещать в checkout, публичный каталог, чат или общедоступные файлы. Утилита печатает только SHA-256 и обезличенные счётчики. `verify` не меняет данные; `import` требует **новый несуществующий** каталог и никогда не перезаписывает существующий. Лимиты — 4 ГиБ и 100 000 записей; при превышении остановиться и пересмотреть процедуру.

```sh
python3 deploy/vps/migration-data.py verify /srv/vargi/source-copy
python3 deploy/vps/migration-data.py export /srv/vargi/source-copy /srv/vargi/private-transfer.tgz --offline-confirmed
python3 deploy/vps/migration-data.py import /srv/vargi/private-transfer.tgz /srv/vargi/imported-data
python3 deploy/vps/migration-data.py verify /srv/vargi/imported-data
sudo chown -R 1000:1000 /srv/vargi/imported-data
```

Пути — примеры. Экспорт требует остановленного/полностью замороженного старого API, включая maintenance и активные загрузки. `--offline-confirmed` подтверждает действие оператора, но не блокирует удалённый сервер. Сверить SHA-256 исходного snapshot, экспорта, импорта и конечного `verify`, числа заявок по каждому статусу и фото. Импортировать в путь, который ещё не создавали через `install -d`, затем назначить его `DATA_PATH`.

Для чтения volume доступен официальный Railway CLI. Использовать авторизованную сессию оператора и отдельный приватный рабочий каталог; не применять `railway shell`/`railway run`, которые загружают переменные сервиса. После остановки записи/maintenance и проверки нужного volume:

```sh
umask 077
railway link --project 32c1bc80-b770-4a05-b708-d9dc974a3dd3 --environment 06dcfcc4-12a3-4a1c-ae2b-57b41976bbc0 --service 679106f2-3404-471a-be30-18ea686f59f2
railway volume files --volume ae025bfd-27a6-4629-990c-1f68507cac9d download /submissions ./source-copy/submissions
railway volume files --volume ae025bfd-27a6-4629-990c-1f68507cac9d download /admin-auth.json ./source-copy/admin-auth.json
railway volume files --volume ae025bfd-27a6-4629-990c-1f68507cac9d download /telegram-notify.json ./source-copy/telegram-notify.json
```

Предварительно создать приватный `source-copy`. Отсутствие необязательного файла допустимо только после проверки, что его действительно нет в volume; ошибка доступа не означает отсутствие. Пути относятся к корню выбранного volume. Не использовать overwrite и не загружать архив с секретами в публичное хранилище. Скачать директорию при продолжающихся изменениях недостаточно для согласованного финального snapshot.

Проверенный свежий приватный daily backup допустим для тестового восстановления; старые daily архивы могли не содержать `telegram-notify.json`, его нужно получить отдельно и повторно проверить полный набор. Перед открытием записи настроить внешние резервные копии и провести восстановление в новый каталог. На новом сервере полный backup собирается в `PRIVATE_TMP_PATH`: достаточно свободного диска и приватные права обязательны. При настроенном S3 и неподтверждённом backup удаление просроченной корзины откладывается. Без настроенного backup обычный maintenance сам по себе не гарантирует сохранность; production нельзя открывать до проверки резервирования.

## Тестовая копия

1. Выбрать VPS и тестовое имя. Проверить доступность IP/HTTPS из проблемной сети. Изменить только DNS тестового имени.
2. Собрать просмотренный commit. Импортировать проверенную копию в отдельный каталог; `MIGRATION_READ_ONLY=1`, `AUTO_MAINTENANCE_DISABLED=1`, новый session secret. Не передавать production Telegram/S3/recovery/setup credentials.
3. Проверить главную, разделы сайта, календарь, `/board/`, все фотографии, `/board/admin/`, `/api/market/health`. URL данных и фото должны содержать только тестовый домен и `/api/market/`.
4. Проверить весь путь подачи/модерации на **другом пустом тестовом каталоге** с отдельным администратором и `MIGRATION_READ_ONLY=0`, уведомления отключены. Не создавать тестовые объявления в копии реальных данных. Вернуть проверенный snapshot в режиме чтения.
5. Повторить проверки с ПК/телефона на проблемном Wi-Fi, мобильной сети и независимой сети. CI не доказывает доступность для этой посетительницы.

Внешний контракт — существующие `/board/`, `/board/submit/`, `/board/admin/`; отдельный старый server-rendered `/market` не используется как новый интерфейс. Все обращения новой сборки идут только на текущий origin; автоматического переключения на старый Railway volume нет.

## Финальное переключение: один сервер с правом записи

1. Сохранить точный старый deployment, DNS, текущий код и проверенный свежий backup. Зафиксировать TTL, A/AAAA/CNAME для apex/www; stale AAAA тоже может направлять посетителей на другой сервер. Проверить HTTPS и резервирование новой системы.
2. Закрыть запись старого API для обоих его доменов и старых клиентов, отключить maintenance, дождаться активных запросов. Только проверенная остановка/заморозка допускает финальный экспорт. Не останавливать рабочий сервис до готовности нового сервера и согласованного окна переключения.
3. Сделать финальный snapshot, импортировать в новый каталог, сверить SHA-256 и счётчики. Старый сервер остаётся без права записи. Не подключать оба API к одному volume и не разрешать запись в две независимые копии.
4. Настроить production `SITE_HOST`/`SITE_ORIGIN`, новый session secret, приватные backup/Telegram credentials. Сначала оставить read-only, проверить чтение и сертификат. При необходимости проверить основной домен через локальное разрешение DNS до общего переключения.
5. Направить apex и www на VPS; NS REG.RU сохраняются. Получить валидный HTTPS для apex/www; включить www override только после подготовки alias. Не отключать проверки TLS.
6. После проверки DNS/HTTPS/чтения включить `MIGRATION_READ_ONLY=0`, `AUTO_MAINTENANCE_DISABLED=0` на **единственном новом API**. Проверить подачу с фото, повтор без дубля, модерацию, публикацию, Telegram и backup/restore. Внешний мониторинг должен подтвердить доставку тревоги при тестовом сбое.
7. Наблюдать из нескольких сетей. Старая вкладка или закешированный JS может обращаться к Railway даже после смены DNS: старый API остаётся замороженным, чтобы не принимать скрытые новые заявки. Старую инфраструктуру не удалять до окончания проверенного периода наблюдения.

## Откат

До появления записей на новом сервере возможен возврат прежних DNS/кода с подтверждённым единственным старым писателем. Если новый API уже принимал изменения, сначала закрыть его запись и maintenance, дождаться запросов, экспортировать весь актуальный набор и сверить обратный импорт на старой стороне. Лишь после этого переключать трафик и открывать старый API. Простой DNS откат после новых заявок скроет их или разделит данные.

Не удалять Railway volume, приватные резервные копии и Caddy volume; не использовать `docker compose down -v`. Откат кода не откатывает данные. Восстановление всегда проводить в новый каталог с проверкой SHA-256.

Официальные справки: [Railway volume files](https://docs.railway.com/cli/volume), [link](https://docs.railway.com/cli/link), [service files](https://docs.railway.com/cli/service).
